O projeto

De aplicação web a aplicativo nativo

Na AA1 entreguei o StrongApp em React, pensado primeiro para tela de celular. A AA2 é a conversão em app móvel — mesmas telas, mesmas regras, mesma API.

  • Escrito em Java, com Android Studio e Gradle
  • Consome a API REST em Laravel do projeto original
  • Autenticação por token pessoal do Laravel Sanctum

Escolha 1

Java nativo no lugar de React Native

A AA1 previa React Native. Mudei de propósito, e assumo o custo.

  • Expõe o ciclo de vida de Activity e Fragment, o RecyclerView, o AlarmManager e o Canvas sem camada intermediária
  • Notificação agendada e geração de imagem já existem no SDK — em RN dependeriam de bibliotecas de terceiros
  • Não havia reuso real de código: a lógica mora no backend
  • Custo: nada é compartilhado com a web, e um iOS exigiria reescrita
Escolha 2

Gráfico desenhado no Canvas

O gráfico de evolução é uma View própria. Nenhuma biblioteca foi adicionada.

  • O projeto precisa de um gráfico de linha, com eixo fixo de 0 a 100%
  • Uma biblioteca traria centenas de KB e um tema próprio para brigar com o do app
  • As cores saem dos atributos do tema: funciona no claro e no escuro sem código extra
  • Uma série só, então sem legenda; rótulo apenas no último ponto
Escolha 3

Lembrete com alarme inexato

O lembrete de treino usa setInexactRepeating, com um alarme por dia da semana marcado.

  • Desde o Android 12 o alarme exato exige SCHEDULE_EXACT_ALARM, permissão sensível e restrita nas lojas
  • Para lembrar de treinar, alguns minutos de atraso não mudam nada
  • Um BootReceiver reagenda tudo depois do boot, porque o Android descarta alarmes ao reiniciar
Problema real

"Não foi possível falar com o servidor"

O app não conectava. Eram duas causas somadas, não uma.

  • A API subia presa em 127.0.0.1 dentro do WSL2 — inalcançável a partir do Windows e do emulador. Correção: --host=0.0.0.0
  • O app tinha gravado um endereço apontando para a porta 8001, de um teste anterior, com a API na 8000
  • Isso revelou um defeito: o botão Servidor só existe na tela de login, então endereço errado prende o usuário depois de autenticado
Verificação

Como sei que funciona

Sem suíte automatizada. Cada requisito foi conferido à mão no emulador, olhando o efeito na API e no banco MySQL.

  • Exercício criado e excluído pelo app, conferido na tabela exercises
  • Superset gravado em workout_exercise_groups com os exercícios ligados
  • Imagem de progresso gerada com 1080×1920 exatos — proporção 9:16
  • dumpsys alarm mostrando os dois alarmes semanais do lembrete
Honestidade

Limitações conhecidas

  • Ranking da Comunidade usa dados fictícios — a API não expõe ranking entre usuários; está dito no código e no README
  • Não funciona offline — toda tela depende de rede
  • O endereço do servidor só é editável antes do login
  • Sem testes automatizados
